[647] assistant: They serve three different purposes:

| Part | Purpose |
|---|---|
| Protobuf contracts | Define the shared data and its meaning |
| Generated `Clone()` methods | Copy that data safely |
| `.go.txt` templates | Hold Go-specific helper code that generators emit |

For example, protobuf declares:

```proto
message ErrorInfo {
  ErrorKind kind = 1;
  string provider = 2;
  string field = 4;
  string message = 5;
}
```

The generator turns that into a normal Go struct. Applications import `sandbox.ErrorInfo`; they don’t import protobuf.

The response contract also declares an `origins` map. That lets the response say “this name came from the request” or “these resources were reported by the provider.”

### Why `Clone()` exists

Your request contains pointers, maps, and slices:

```go
request := &sandbox.CreateOptions{
    Environment: map[string]string{"MODE": "test"},
}
```

A normal assignment shares the map:

```go
copied := *request
copied.Environment["MODE"] = "changed"

// request.Environment["MODE"] is now also "changed".
```

Generated `Clone()` creates an independent map:

```go
copied, err := request.Clone()
copied.Environment["MODE"] = "changed"

// The original still contains "test".
```

Kit uses this internally for requests and response metadata. You normally don’t need to call it yourself.

Previously, we copied through JSON. That could change numbers inside arbitrary metadata into `float64` and lose precision. Typed copying avoids that conversion.

### What `.go.txt` contains

These are **generator templates**, not application code:

```text
tooling/internal/go/types_gen/templates/
    errors.go.txt
    clone.go.txt
```

- `errors.go.txt` contains Go’s error-wrapper behavior: `Error()`, `Unwrap()`, and preserving causes.
- `clone.go.txt` contains the helper for copying arbitrary metadata values.
- The generator substitutes settings such as the maximum nesting depth and emits ordinary `.gen.go` files.

The SDK compiles those generated `.go` files. It never reads `.go.txt` at runtime.

One distinction matters: the schema determines the fields and generated `Clone()` methods. The templates contain helper algorithms that Go needs to operate on those fields. They are handwritten Go stored inside the generator—not logic defined by protobuf.

That template choice isn’t essential. We could emit those helpers using `g.P(...)` like the existing generators if you prefer one consistent generation style.
